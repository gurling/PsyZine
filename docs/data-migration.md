# Moving a journal to PsyZine

PsyZine direct releases install as `app.psyzine`; debug uses `app.psyzine.debug`. The optional Play variant uses `.play` before `.debug`. Keep the original installation available, export its journal as JSON, then import in PsyZine after the replacement confirmation. Android applications cannot read another application’s private database.

The archived public JSON format and PsyLog’s verified Android Journal conversion format are supported. Newer-format units use stable string-ID remapping and recursive ingredient references. Known single-ingredient quantities/uncertainties are retained; multi-ingredient products become custom products with their full source composition in descriptions/notes, so no unsupported single-ingredient estimate is inferred. Original custom substances, repeated definitions, notes, dates, routes, and ingestion counts are retained. Cycles, missing/ambiguous references, unsupported export sources, invalid numeric values, and unrelated JSON are rejected before mutation. Synthetic source-derived fixtures are tested; authoritative exports from newer private upstream releases are unavailable, so compatibility beyond the observed format is unverified.

## Room compatibility

Schemas 1–7 are unchanged. PsyLog’s schemas are structurally identical and require no extra feature migration. Room still supplies the original automatic 1→7 chain, followed by explicit manual 7→8. Schema 8 adds indexed `photo_attachment` with a cascading Experience foreign key and `journal_state` with a journal generation token. No destructive fallback is used.

Schema 1’s Experience CREATE omitted AUTOINCREMENT, despite the later schema snapshots including it. Room’s original generated 1→2 migration is empty. The 7→8 migration detects that actual legacy SQL shape and rebuilds only that parent table, copying every original column and ID, then renames it before creating the attachment table. This repairs deleted-ID reuse without changing journal content. Other starting schemas retain their original parent table. Generated migration SQL and this repair have passed SQLite preservation/shape/sequence/cascade checks; the Android MigrationTestHelper test covers every supported start version and remains pending a device run.

Experience insertion now aborts conflicts and allocates parent IDs through Room before related records. Editable title/text/location updates preserve dates and favorites; clearing location also clears its coordinates. Complete deletion includes timed notes, ratings, ingestions, and attachment rows. Clearing the journal invalidates old drafts/intents in the same transaction. Restores allocate a fresh generation so an old editor cannot overwrite an imported entry with a reused ID. Custom-unit/substance and final ingestion editors also retain that generation across recreation and validate it in their mutation transaction; failed saves stay on screen. Substance edits update the existing row instead of using REPLACE.

## Portable backups

Default `.psyzine` ZIPs contain `manifest.json` (format `PsyZine`, version 1), journal content, theme key, optional presentation preferences, photo records linked to experience indices, processed images, and SHA-256 checksums. The optional presentation fields remain backward compatible with earlier format-1 manifests. Permission-request history and onboarding consent are never restored from an explicit backup. JSON export is explicitly entries-only, omitting photos and appearance/presentation preferences.

Restore validates archive names, extraction limits, references, checksums, image decoding, normalized orientation/location metadata, and expected entry sets before replacement. Duplicate ZIP entries, extra/missing images, traversal, and oversized/corrupt inputs are rejected. Photos are staged and promoted to fresh UUID paths before a single replacement database transaction. Failed operations remove promoted files and retain the old journal/photos. Cancellation before commit retains old data; the commit is non-cancellable. Appearance/presentation writes happen afterward and report a separate warning on failure. A failed export is reported as incomplete and may leave a partial file at the chosen provider; do not treat that file as a completed backup. SAF providers do not offer a universal atomic file replacement operation.

Limits are 64 MiB for JSON/manifest bytes, 2 GiB for extracted archive bytes, fewer than 10,000 photos/entries in one archive, 100,000 experiences/custom units, and 1,000,000 ingestion/rating/timed-note records. Validation uses actual streamed bytes rather than trusting ZIP declared sizes. Image payloads are capped at 50 MiB. An allocation failure is recoverable and does not replace the journal. Explicit backups are not encrypted and may contain sensitive journal/location data; you control the destination.

## Photos and interrupted operations

Imported images remain usable after the source is deleted or unavailable. Source input is limited to 50 MiB, 100 million pixels, and 32,768 pixels per dimension. Decode sampling limits the working image to eight million pixels and 5,120 pixels per long edge before orientation copies; final output has a maximum 2,560-pixel long edge. Opaque images use JPEG quality 85; transparency is kept as PNG. EXIF rotation/mirroring is normalized and normalized pixels are encoded without EXIF/XMP/location metadata. Thumbnails have a maximum 384-pixel edge and can be regenerated. HEIC/AVIF support follows the device decoder; unsupported inputs produce retry/remove errors.

Acquisition permits at most 20 photos per batch, including SAF results; an experience has no fixed attachment total. Processing is sequential off the main thread. Completed files survive another image’s failure. Temporary URI access is held for interrupted acquisition and released after copying, saving, discarding, or journal replacement. Camera capture uses a narrow, non-exported FileProvider for private camera staging only and requires no broad storage or CAMERA permission.

New photos/removals remain staged until Save. Atomically written draft manifests retain entry text, attachment identifiers, pending capture, pending sources, and per-image failures across recreation. Save promotes fresh files, verifies generation and parent existence, then commits editable fields plus attachment records together. Discard removes new draft files and preserves saved photos. Allocation/disk/save failures leave the journal and recoverable draft intact. Generation changes reject old drafts after restore/clear.

Startup reconciliation keeps referenced files and active drafts, collects orphan images/thumbnails/staging/camera files after a 24-hour grace period, and retries failed deletion on later starts. A corrupt draft manifest stops collection rather than guessing which files to delete. Cache loss regenerates thumbnails.

## Privacy and upgrades

Journal database, attachment bytes, and staging files are explicitly excluded from legacy cloud backup and Android 12+ cloud/device-transfer rules. The existing preferences DataStore remains eligible, including appearance/display settings and last/clone workflow timestamps. Read [PRIVACY.md](../PRIVACY.md) for notification/widget visibility and provider behavior.

Direct releases must retain `app.psyzine` and the same independent signing key for upgrades. Test installation alongside upstream, backup transfer, and signed PsyZine upgrades on an isolated test device before distribution. No APK/device/signing test has run in the current constrained environment.
